## 三 · 问题 3：画布各框孤立、大小颜色相同、无分层

**这是真问题**，而且是**设计与信息表达**层面的，不只是样式。

你报的三件事，其实是三个不同的缺陷：

| 你看到的 | 本质 | 违反 |
| --- | --- | --- |
| 天宽的信息**都是关联的，但没关联起来** | **AI 没做关系推断** —— 画布只画了对象，没画对象之间的关系 | 宪章一（连接）、03 §5 关系与画布 |
| 每个框**大小、颜色都一样** | **没有视觉分层** —— 看不出哪个是主、哪个是次 | VI §9（关系与画布的视觉语言）、宪章六「精致」 |
| 没有**直观简洁表达和分层** | 缺少"一眼看懂这张图在讲什么"的层次 | 宪章六「有重量」 |

### 用户 2026-10-16 已定三条决定（不再需要讨论）

**① 关联从哪来 —— AI 推断，但推断必须先存在**

> 用户原话：「AI 推断的关系必须**虚线 + 可点否决**，前提是现有推断，**现在是连虚线都没有**」

**实测确认用户判断正确**（真实库）：
```
业务对象 16 个（任务5·材料3·议题2·项目2·事务2·组织1）
关系记录  2 条        ← 16 个对象只有 2 条关系，而且 type 是空的
```
**画布有框、几乎没有线。** 所以第一步不是"画线"，是**先让推断存在**。

规范要求（用户原话，2026-10-13 与本次一致）：
- **AI 推断的关系 = 虚线**（与用户手工确认的实线区分开）
- **可点否决**：点一下就能说"这条不对"，否决后不再出现
- **带依据**：为什么认为它们有关系（宪章八：不许无依据）
- 手工连线默认是**画布注释**；只有明确赋予关系类型并提交才进入业务关系

**② 框大小 —— 按"节点在关系网里的分量"，由 AI 判断**

> 用户原话：「不要都很大，要**精致**一些；**不要重要和紧急**，而是**节点** ——
> 比如**项目是个大节点**，里面**任务是小节点**；**联动很多的知识是个重要的**，**小知识**就不是很重要」

| 对象 | 大小 | 依据 |
| --- | --- | --- |
| 项目 | **大** | 它是一组任务的容器 |
| 任务 | **小** | 属于某个项目 |
| 被很多对象引用的知识/议题 | **大** | 连接度高 |
| 孤立的小知识 | **小** | 连接度低 |

**判据**：大小 = **连接度 + 层级**（由 AI 判断），**不是** priority/urgency。
**"精致"是硬要求** —— 现在的框都太大了，要收小。

**③ 框颜色 —— 按类别**

> 用户原话：「应该按**类别**吧，项目、任务、知识、企业、日程等等」

| 类别 | 颜色 |
| --- | --- |
| 项目 | 一色 |
| 任务 | 一色 |
| 知识（议题/材料） | 一色 |
| 组织 | 一色 |
| 日程（事务） | 一色 |

**注意**：颜色定类别（是什么），**不承担判断**（VI §2：颜色不得单独承担判断）；
所以每个节点**仍要有文字标签**，不能只靠颜色区分。

### 这一条的正确做法（不是 I 猜的，是三条决定推出来的）

```
1. 先做「关系推断」：AI 读已有对象与材料 → 提出候选关系（每条带依据）
   · 推断结果**先进收件箱**（AI 提议才进收件箱 = 契约②），不是直接画到画布上
   · 用户同意后 → 实线；否决 → 不再提
2. 画布上：确认过的关系 = 实线；**未处理的推断 = 虚线 + 可点否决**
3. 节点大小 = 连接度 + 层级（AI 判），**框要收小**
4. 节点颜色 = 类别
```

**现在就做第 1 步的前提检查**：现在的 `relation` 只有 2 条、`type` 还是空的 ——
先弄清**为什么推断没产出**（是没跑、还是跑了没落库、还是落了但没画）。
