## 一 · 宪章要不要改？—— **不用改条文，但要补一条边界**

**查证结论（逐条对过）**：宪章 v1.2 **本来就支持"发布成产品"**：

| 条 | 原文 | 对"发布产品"的支撑 |
| --- | --- | --- |
| 序 | 「它服务一个人，但一个人做完事留下的信息与知识，**本就不该只停在一个人手里**」 | ✅ 直接支持 |
| 第一条 | 「**向外**：让这个人的判断与积累，反过来成为组织可复用的资产」 | ✅ "向外"就是发布 |
| 第二条 | 身份三「组织的知识源：把沉淀结构化，按授权分享；**产出可被别人直接拿走用**」 | ✅ 支持 |

**所以不需要改这三条。** 但宪章**没说清一件必须说清的事**：

> **产品公开 ≠ 数据公开。**
> 代码可以进公开仓库，业务数据（录音、会议纪要、客户信息、判断原文）**永远不出去**。

这一条现在是**隐含**的，而接下来就要公开发布 —— **隐含的边界在第一次发布时最容易被踩破**。

**建议**：按第九条流程，在第八条「边界：明确不做」下**补一款**：

> **不做把个人数据带出本机的事。** 产品代码可公开；业务数据、录音、判断原文、凭证
> **不得进入任何仓库、不得上传、不得随包发布**。对外分享一律是**你主动选出并授权的产出**，
> 默认关闭（与第二条"身份三 = 分享产出，不是多人共编"一致）。

- 版本升 **v1.3**；理由与讨论记录进修订表；v1.2 原文归档

### 原始资料怎么规划（你的第 3 问）

`voice`(251M) 与 `_archive`(80M) 性质不同，**不能一刀切**：

| 资料 | 性质 | 规划 |
| --- | --- | --- |
| **`voice/`** | **原始输入**（录音原件）—— 是"事实的源头"，转写文本由它派生 | **进数据根**；同步（它是可编辑业务的原料）；**不进仓库** |
| **`_archive/`** | **历史快照**（旧版本、旧备份）—— 不可编辑、只用于回溯 | **进数据根**；**不同步**（体积大、且是派生备份）；不进仓库 |
| **`research/` `patches/`** | 开发过程的中间物 | **进仓库**（它们解释"为什么这么改"） |
| 项目文件夹（如 `微纳核芯-…/`） | **业务材料** | 进数据根；同步；不进仓库 |

**判据**：**"原始"与"派生"分开对待** —— 原始（录音、纪要原件）要保护、要同步；
派生（备份、导出、构建产物）可重建，不必同步。

## 三 · 规范统一管理（你的第 3 问后半）—— 现在的状态是**腐烂的**

**实测现状**：`spec/` 下 **16 个文件，其中 4 组同号**：

```
05-常驻部署方案          / 05-现状评估与改造清单
06-Goal定义与连续工作协议 / 06-双端同步设计
08-Mini失联恢复与常驻加固 / 08-逐条验收-最初目标与宪章
12-修复进度账本          / 12-目录重构为可发布产品
```

**编号重复意味着"顺序"这个信息已经废了** —— 而规范的顺序正是"先读哪份"的答案。

### 定规范体系（三层，各有各的职责）

```
第 0 层 · 宪章            01-顶层宪章           ← 只定义不可让渡的（九条）
第 1 层 · 规范            02-VI 规范
                          03-功能与交互设计
                          04-开发规划与约束
                          13-技术与架构规范      ← 新增，技术侧最高规范
第 2 层 · 设计与方案      05-常驻部署 06-双端同步 09-设置页定时 …
第 3 层 · 记录与审计      08-逐条验收 11-符合性审计 12-进度账本 …
```

**规则**：
1. **编号唯一**，按层分配段位（0x = 宪章与规范；1x = 设计与方案；2x = 记录与审计）
2. **改名不改内容** —— 同号文件按上述分层重新编号，旧文件名在索引里留一行说明
3. **每份规范第一行必须写**：依据哪条宪章、状态（讨论中/冻结）、版本、修订记录
4. **规范目录里必须有 `README.md` 索引**：谁读谁、谁被谁约束

## 四 · 规划怎么做 + **门禁先行**（你的第 4、5 问，这是最关键的一问）

**你的直觉是对的：门禁要先做。** 理由很直接 ——

> **规范在没有门禁之前，只是一段愿望。**
> 这一轮里"规范写着要分离代码与数据，而同步引擎一直在同步代码"，就是活例子。

### 顺序（每一步的产物都是下一步的输入）

```
① 宪章补边界（第八条加一款）→ 升 v1.3，旧文归档
        ↓
② 规范分层 + 编号唯一 + 建索引        ← 让规范本身可查、可引
        ↓
③ **为每条新规范先写门禁**（写完立刻跑，允许先红）
        ↓   ← ★ 关键：门禁先于改造
④ 跑门禁 → 红的部分列成改造清单
        ↓
⑤ 一次性改造（你说可以一次改）
        ↓
⑥ 门禁转绿 → 才算交付
```

### 先要做的门禁（对应第 1、2、7 条原则）

| 门禁 | 查什么 | 现在跑会怎样 |
| --- | --- | --- |
| **代码与数据分离** | 仓库里**不得**出现录音/纪要/`.sqlite`；`.gitignore` 必须覆盖产物 | **会红**（现在同目录） |
| **数据根不在受保护目录** | 数据根不得在 `~/Desktop`、`~/Documents`、`~/Downloads` | **会红**（现在就在桌面） |
| **依赖方向** | `src/` 不得 import `prototype/` | **会红**（`browser-api.mjs` 现在就引了） |
| **规范编号唯一** | `spec/` 下不得有同号文件 | **会红**（4 组重复） |
| **规范每份有依据/状态/修订记录** | 头部必须有这三样 | **会红**（多数没有） |
| **版本可辨认** | 打包版本与 `package.json` 一致；同版本不得有两个产物 | ✅ 已绿（`install:local` 已实现） |

**门禁先写、允许先红、红了就是改造清单** —— 这样改造才有明确的"改完了没有"。
