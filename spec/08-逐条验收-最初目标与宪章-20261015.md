### G6 为什么是"没做到"，以及证据链

**不是插件的问题**——从**笔记本**直接打飞书官方接口（不经插件、不经 mini）：

```
POST https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal
→ code 21001, "Access denied by access control policy"
POST https://open.larksuite.com/...（换域名）
→ code 21001，同样
```

结论：**飞书服务端在拒绝这对凭证**。排除了插件与搬家两个变量。
具体是哪条访问控制策略（IP 白名单 / 应用停用 / 可用范围）**看不到后台无法判定**，不猜。

### 第八条 · 本轮抓到并修掉的两处「明确不做」

1. **无回执的假成功**（连着改第二个字段必失败、而界面显示"已改"）
   根因两处断链：`api.mjs` 取错误码读错了字段（服务端放在 `error`，代码读 `code`）→ 冲突重放分支成死代码；`inlineChange` 用 `report()` 包住写入 → 失败被吞。
   **修后实测**：连改两处都成功、库里值正确、失败时值会还原并如实报「没能保存」。
2. **前端崩溃**（切到时间路线图后，同意任何一条改动都崩）
   栈：`renderProjectStrip ← renderWithFilters ← project-filters 监听`。根因：`body.innerHTML` 重写后 `.projectstrip` 消失，`querySelector` 返回 null 仍写 `innerHTML`。
   **修后实测**：页面错误 3 条 → **0 条**。

## 三 · 规范覆盖（机械检查）

```
node prototype/spec-coverage-audit.mjs
→ 四份规范共 75 条 —— 有门禁 46 · 明确靠人工 29
→ PASS：每条规范都有明确的责任人
```

它保证不了"门禁本身判得对"，但保证**没有任何一条规范是悄悄没人管的**：
- 新增一条规范却没有责任人或人工说明 → **红**
- 声明的门禁不存在、或没在 verify 链里跑 → **红**
- 标"靠人工"但没写清"人工看什么" → **红**
- 规范删了条款而对照表还留着（表腐烂）→ **红**

**它已经抓到过我一次**：我曾把动效门禁挂到一个**不存在的条款** `VI · 10 · 动效`（VI 里 10 是"分享与导出形态"）——是我凭印象编的。
