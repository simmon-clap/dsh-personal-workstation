## 0 · 为什么需要它

2026-10-15 查证出一个硬事实：**DSH 桌面客户端只连本机 Host**（客户端包内没有任何"连远程 Host"的选项，只用过 `127.0.0.1:19387`）。

所以下面三件事**不能同时靠配置实现**：

1. 笔记本用**桌面客户端**
2. 笔记本**离线可用**
3. 两边**一致**

用户选择要全部三件 → **两边各跑一个完整 Host，中间加同步层**。

```
笔记本：DSH 桌面客户端 + 工作台插件   ← 自己的 Host、自己的库
mini：  DSH Web（常驻）+ 工作台插件    ← 自己的 Host、自己的库
                    ↕
              同步层（本文档）
```

---

## 1 · 为什么这不是从零造

工作台的数据模型**本来就是为了"并发编辑 + 版本冲突"设计的**。同步引擎需要的东西，它已经有了：

| 同步需要 | 工作台已有 |
| --- | --- |
| 两边新建的对象不会撞 id | ✅ id 是 UUID |
| 能判断谁新谁旧 | ✅ 每个对象带 `revision` 与 `updatedAt` |
| 能交换"变了什么" | ✅ 变更日志表（每次 draft/commit 都记） |
| 删除怎么同步 | ✅ 归档是软删（`archived`），天然适合同步 |
| 冲突策略 | ✅ 契约③已定：版本冲突时**用最新内容重放你自己的字段改动** |

**结论：同步层不是发明新机制，是把已有的版本机制用在两台机器之间。**

---

## 2 · 冲突策略：以最新为准（用户 2026-10-15 拍板）

用户判断：**两边同时改同一份的概率很低**，所以按"最新的保存"即可。

同意。但必须补一条，否则会踩宪章第八条。

### 2.1 风险：LWW 的失败模式是"静默"

「以最新为准」听起来是"保留较新的那个"，实际发生的是 —— **较旧的那次改动被丢掉，而做那次改动的人不会收到任何提示**。

那正是宪章第八条列在"明确不做"里的「**无回执的假成功**」：用户以为改成了，其实没有。

### 2.2 折中：照用 LWW，但被覆盖的要留痕

| 场景 | 处理 |
| --- | --- |
| 两边改的是**不同对象** | 正常合并，**零提示** |
| 两边改的是**同一对象、不同字段** | 按契约③重放，**零提示** |
| 两边改的是**同一对象、同一字段**（真冲突） | 采用较新的一次；**在收件箱留一条**：「X 在另一台机器上被改过，这次采用了较新的版本，你的改动没生效」，可展开看被覆盖的内容 |

概率低 → 日常几乎不会出现；真出现 → 有回执、可追溯、可撤销。**既简单又不撒谎。**

### 2.3 一个必须处理的技术细节：两台机器的时钟不同

判断"谁最新"用的是时间，而两台机器的时钟可能差几分钟。若直接比 `updatedAt`，**较旧的那次会被误判为最新**。

做法：**统一时间源** —— 两边的写入时间都跟常驻节点（mini）对齐；离线期间写入的，同步时按"本地单调序号 + 节点校准时间"折算。**不能用两台机器各自的墙上时钟直接比。**

## 3 · 同步什么

| 内容 | 怎么同步 | 冲突 |
| --- | --- | --- |
| **业务对象**（项目/任务/判断/资料/事务/关系…） | 对象级增量交换（用 `revision` + 变更日志） | 见 2.2 |
| **材料文件**（Office 改的那些） | 点对点文件同步（Syncthing 一类） | 采用较新；被覆盖的按 2.2 留痕 |
| **工作台配置**（授权目录等） | **不同步**，各机器各自配置 | — |
| **DSH 会话记录** | **不同步**（那是 DSH 自己的持久化） | — |
| **密钥与凭据** | **不同步** | — |

> 最后三行是刻意的：同步范围越大，出错面越大。只同步"业务事实"，其余各归各家。

---

## 4 · 何时同步

| 时机 | 行为 |
| --- | --- |
| 启动时 | 先拉一次，再让用户操作 |
| 在线时 | 按间隔增量交换（建议 1–2 分钟，或每次提交后） |
| 提交本地改动后 | 立即尝试推一次；失败就排队（断网是常态，不是异常） |
| 长时间离线后 | 见第 5 节 |

**断网不是错误路径**：契约②已经定了"断网保留草稿给重试并复用同一幂等键"，同步层沿用这个思路 —— 队列化、幂等重试。

## 4b · 判活：记账，不探活（v1.1 补，2026-10-21）

`dsh-sync.sh` 原来用 `ssh -o ConnectTimeout=8` 探活。2026-10-21 按日志核实，两处都不对：

- **误判**：Tailscale 走中继时 8 秒不够，于是报「对端不可达」，而常驻节点其实在线（当晚实测 SSH 通）。
- **掩盖**：失败被写成「跳过这次（**不算失败**）」，既不告警也不留可判读的记录；同时"最后成功时间是 10-19 16:30"这件事，只有翻日志才知道。

| 旧做法 | 新做法 |
| --- | --- |
| ssh 探活，超时即"不可达" | 常驻节点每 15 分钟写一条 `beat{at, seq}` 到同步库；判活只读这一条 |
| "不可达"= 一种失败 | 必须区分**哪一侧 / 哪一跳 / 什么原因**（网络 / 进程 / 定时任务未加载） |
| "不可达"可以"不算失败" | 常驻节点不可达**是失败**并告警；其他端不可达是常态，**不记失败**（宪章 v1.4 承诺不对称） |
| 只看有没有报错 | 状态面必须给出：最后成功同步、连续失败次数、失败在哪一跳 |

**门禁**：`npm run verify:liveness`（判据 S14–S16，见 [48 语义门禁清单](48-语义门禁清单-v1.0.md) §11）。脚本为 `workstation/prototype/sync-liveness-audit.mjs`，带 `--self-test`（4 个夹具 canary）。

## 5 · 离线多久算太久

用户明确要"离线可用"。但不能无限期：两台机器各自离线一个月，再合就是大量冲突。

建议**分档**：

| 离线时长 | 行为 |
| --- | --- |
| < 1 天 | 完全无感 |
| 1–7 天 | 正常合并；若有被覆盖的改动，按 2.2 留痕 |
| > 7 天 | **同步前先提示**："你已离线 N 天，这次合并可能覆盖较多改动，先看一遍再合" —— 一次确认，不是每次都问 |

## 5b · 微信接入点：只能挂一台（2026-10-15 用户提问）

**问**：两边都登录同一个 DSH 账号、插件配置也一样，微信有会话时能不能**自动选** mini 或笔记本处理？

**答：不能按会话自动选节点。** 原因是机制层面的硬约束，不是配置问题：

- 微信渠道走**扫码登录**，那条连接是**单一会话**。两个 Host 都配同一个微信号 → **互相踢**。
- IM Connect 的配置模型是「一个渠道 → 绑定一个 `cwd`、一个 Host」，没有"按消息选节点"这一层。

**所以：微信只接一台。建议接 mini**（它常驻、24 小时在线，这正是常驻节点的意义）。

### "自动选节点"是另一件事，而且现在没有

它是**任务级路由**（这件事在哪台机器执行），不是微信级。你知识库里那份《DSH 底座研究与实施方案》已经写过这一条：

> 「V1 的执行目标选择可先使用**明确的任务级路由**：本机处理仅本地材料，Mini 处理已同步材料；保留统一任务记录。……**双向分布式调度和运行中进程迁移不是已验证的原生能力**。」

所以现在**只能做明确指定，不能做自动选择**。要自动，得先有可验证的机制（当前 DSH 里没有 SSH/远程执行器这层 —— 已查证）。

### 实际上大多数任务不需要选

因为两边**同步同一份业务数据**，绝大多数任务在哪台跑，结果都落进同一个库，没有区别。只有两种必须指定：

| 情况 | 必须在哪台 |
| --- | --- |
| 要用**笔记本上的本地软件 / 本地文件** | 笔记本 |
| 要**常驻 / 定时 / 你不在的时候**做 | mini |

### 账号与配置相同，不会让两个 Host 变成一个

账号只管**模型访问**；插件配置一样只让**行为**一致。**它们不会合并成一个 Host** —— 两台机器仍是两个独立的库，靠同步层保持一致。

## 6 · 明确不做

- ❌ **不做实时协同编辑**（两人同时改一个字那种）。这是单用户工作台。
- ❌ **不同步密钥、凭据、DSH 会话**（第 3 节）
- ❌ **不同步工作台配置**（授权目录各机器各自配，避免"我以为是同一份授权"的错觉）
- ❌ **不做"以最新为准"之外的自动合并猜测**（比如按字段猜意图）—— 猜错比覆盖更坏
- ❌ 不在文件同步里做"自动选边不留痕"

## 附 · 怎么跑（操作手册）

```bash
cd workstation
# ① 只读检查差异（不动任何数据）
node sync-engine.mjs \
  --local  ~/…/workstation-data/workstation.sqlite \
  --remote simmon@simmondeMac-mini.local \
  --remote-db /Users/simmon/DSH/飞书工作区/workstation-data/workstation.sqlite

# ② 真同步（对象 + 材料文件）
node sync-engine.mjs …（同上）… --apply --force \
  --files --local-root ~/Desktop/DSH/飞书工作区 --remote-root /Users/simmon/DSH/飞书工作区
```

**为什么走 SQLite 直连而不是 HTTP**：mini 那边的 HTTP 要访问令牌（只在 App 内存里，不落盘）。
两边的库都是 SQLite 文件、都能直接读 —— 直连绕开认证，也就能自动化。

**退出码**：`0` 成功 · `1` 仍有差异 · `2` 参数错 · `3` 长离线需要 `--force`。

**范围**：同步 `entities`（业务对象）+ 根目录材料文件。
**不同步**：会话记录、凭证、`workstation-data`（各自的数据库，走对象级）。

## 附 · 实现中踩到的两个坑（记下来免得重犯）

1. **远端 SQL 不能拼进命令行**：`execFileSync('ssh', [...])` 的每个参数会被 ssh 拼成一条远程 shell 命令再解析一次，数据里带 `"` 时被 shell 吃掉 → `unrecognized token`。改成 **stdin 传 SQL**。
2. **校验口径必须与 rsync 的排除口径一致**：第一版 rsync 排除了 `workstation-data`，但文件清单校验没排除，于是把"两边本来就该不同的数据库文件"报成不一致（一次假报 5190 个）。
