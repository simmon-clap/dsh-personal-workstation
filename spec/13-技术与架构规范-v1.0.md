## 0 · 这份规范解决什么问题

现在的技术现状是**"能跑，但没有骨架"**：

- 代码和业务数据在同一个目录里 → 同步引擎在同步代码（实测 5199 个文件里混着大量源码）
- 目录在桌面上 → 后台任务被 macOS 隐私保护挡住（定时同步实测退出码 126）
- 没有 git → 无法版本化、无法发布
- 版本号长期不动（2.3.0 用了十几轮改动）→ 分不清新旧
- 脚本散落在 `~/.dsh/bin/`、`~/Library/LaunchAgents/`、仓库里 → 没有归属

**这些不是"整理一下就好"，它们各自都在制造真实故障。** 本文先把骨架定下来。

---

## 1 · 第一条原则：代码与数据必须分离

**从宪章推**：第一条（连接你的世界）意味着**数据是你的**；第八条（明确不做）意味着**不做拿不到回执的事**。
代码与数据混在一起时，同步、备份、发布三件事会互相污染——**这是架构问题，不是收纳问题**。

| 类别 | 例子 | 去哪 | 为什么 |
| --- | --- | --- | --- |
| **代码** | `src/` `prototype/` `client/` `skills/` `spec/` `design-system/` `test/` `scripts/` | **仓库**（git） | 要版本化、要发布、要能回滚 |
| **业务数据** | 数据库、录音、会议纪要、项目材料 | **数据根**（不是仓库） | 里面有客户信息与录音，**绝不能进公开仓库** |
| **临时产物** | 构建输出、截图、`.syncbak`、日志 | 仓库内 `dist/` 或 `~/.dsh/`，**gitignore** | 可再生，不进版本 |

**可检查的判据**：
- 仓库根目录里**不得存在**业务数据文件（录音/纪要/数据库）
- `.gitignore` 必须覆盖 `releases/`、`*.syncbak-*`、`screenshots/`、`*.sqlite`
- 数据根**不得位于 `~/Desktop`、`~/Documents`、`~/Downloads`**（macOS 隐私保护会挡住后台任务 —— 实测 `Operation not permitted`）

## 2 · 第二条原则：依赖方向单向，不出现环

**从宪章推**：第七条（长期性）—— 能活很久的代码，模块边界必须清楚，否则改一处崩一片。

```
        ┌──────────────────────────────────────┐
        │  prototype/  界面（可替换）           │
        └───────────────┬──────────────────────┘
                        │ 只能往下依赖
        ┌───────────────▼──────────────────────┐
        │  src/  服务端：store / 校验 / 路由    │
        └───────────────┬──────────────────────┘
                        │
        ┌───────────────▼──────────────────────┐
        │  DSH 宿主能力（tools / sessions / …） │
        └──────────────────────────────────────┘
```

**硬规则**：
- **界面层不得直接读写数据库**（必须经 `browser-api` 的动作）
- **服务端不得 import 界面模块**（现在是反的：`browser-api.mjs` 引了 `prototype/` 里的东西）
- **插件对宿主能力一律用 `ctx.get?.(…)` 可选获取，不写进 `inject`** —— 除非缺了它插件确实起不来

**可检查的判据**：加一条静态检查——`src/*.mjs` 不得 import `prototype/`；`prototype/*.mjs` 不得 import `node:fs`。

## 3 · 第三条原则：多端是**对等副本**，不设唯一权威

**从宪章推**：第七条 v1.2 已明确 ——「多端是对等副本，不设唯一权威节点；删除必须留墓碑；被覆盖的那一次必须在两端都留痕」。

| 推论 | 技术要求 |
| --- | --- |
| 没有主从 | 两台机器跑**同一个插件、同一个版本**，谁都不是"服务端" |
| 冲突能收场 | 对象级 `revision` + 统一时间源；**以最新为准，但被覆盖方必须留痕** |
| 删除不复活 | 删除写**墓碑**（`archived` + 删除时间），同步时墓碑优先级高于"对端没这条" |
| 密钥不跨端 | 会话记录、凭证、工作台配置**不进同步范围** |

**当前实现与规范的差距（2026-10-21 按运行日志与代码核实，原文第三条已更正）**：
- ✅ **删除复活：墓碑已实现** —— `store.mjs` 有 `tombstones` 表；双端同步日志有 `PASS tombstones 指纹`。
- ✅ **心跳/出声反馈已在同步范围** —— 同步日志实见 `heartbeat_runs`、`speak_feedback` 的拉/推记录。**原文"心跳/出声反馈/审计三张表不在同步范围"已不成立，此处更正。**
- ❌ **审计（audit）仍未在同步范围** —— 同步日志只出现 `heartbeat_runs` / `speak_feedback` / `batches` 三类。
- ❔ **覆盖是否双侧留痕：未核实** —— 本轮没有实测证据，不写成"已修"也不写成"未修"。

## 4 · 第四条原则：能力一律"可选接入"，不许硬绑

**从宪章推**：第八条「未接入不伪造」+ 约束三。

| 场景 | 做法 |
| --- | --- |
| 调度（实验性 bundle） | `ctx.get?.('schedule')`，取不到就在界面写「未接入」，**不给假按钮** |
| 日历 / 飞书 / IM | 同上；未接入时如实说明，不假装 |
| 依赖版本 | 与宿主**同版本**；跨版本只在 `spec/` 里记录依据，不靠"应该兼容" |

**可检查的判据**：`npm run verify` 里必须有"未接入路径"的测试 —— 断言服务缺失时**不崩且如实说明**。

---

## 5 · 第五条原则：每一次交付都要"可辨认"

**从宪章推**：第八条（无回执的假成功）+ 用户 2026-10-16 的明确要求。

| 要求 | 做法 | 判据 |
| --- | --- | --- |
| 版本能分辨新旧 | **语义化版本**，每次发布必须递增 | 版本不变却有改动 → 门禁红 |
| 产物能核对 | 每次打包用**唯一文件名**（含时间戳） | 同一版本号出现两个不同产物 → 门禁红 |
| 界面能看见 | 设置页「版本说明」显示版本 + 构建时间 + **是否需要重启** | 见第 6 条 |
| 发版前跑门禁 | `npm run verify` 必须 `EXIT=0` | 有失败仍发版 → 视为未交付 |
| 一条命令装 | `npm run install:local`（构建→打包→指向→非交互安装） | 手工复制产物 → 视为未交付 |

**为什么"是否需要重启"要写在界面上**：实测过 —— 用户重启了两次却什么都没变，因为**装的包和跑的实例不是同一个**，而界面上从没说"你现在看的不是最新的"。

## 6 · 第六条原则：验收看"用户能不能用"，不看"我装上了"

**从宪章推**：用户多次反馈「你说的没实现/找不到」，根因已查明：

> **用户浏览器里跑的那份，既不是仓库里的、也不是已装包里的。**

| 层次 | 证据长什么样 | 够不够 |
| --- | --- | --- |
| 文件在 | `ls` 能看到 | ❌ |
| 进程在 | `pgrep` 有输出 | ❌ |
| 路由通 | HTTP 401 | ❌ |
| **用户路径走得通** | **真实入口点进去、点得动、有数据** | ✅ 只有这个算 |

**铁律**：任何验收之前，**先核对"浏览器实际加载的模块 = 意图交付的那个包"**（比哈希），再谈功能对不对。门禁全绿与此**无关**。

## 10 · 常驻节点：心跳与租约（v1.1 新增）

**从宪章推**：第七条（长期性）+ v1.4「承诺不对称」——只有常驻节点承担"必须在线"，笔记本与手机不承担。

| 要求 | 做法 | 为什么 |
| --- | --- | --- |
| 判活靠**记账**，不靠**探活** | 常驻节点每 15 分钟写一条 `beat{at, seq}` 到同步库 | ssh 探活超时会把"我这边连不上"说成"对端不可达"；记账能把两者分开 |
| **单向承诺** | 常驻节点不可达 = 故障；其他端不可达 = 常态，**不记失败** | 两端期望不对称，用同一套判据必然误判 |
| 失败要能分辨 | 记录**哪一侧、哪一跳、什么原因**（网络 / 进程 / 定时任务未加载） | 一句"不可达"同时掩盖三种完全不同的故障 |
| 不靠模型 | 全部是时间戳比较与计数，**0 token** | 稳定性判断不该有模型不确定性 |
| 恢复 | 常驻节点回来后补跑一次（幂等）；其他端打开时拉一次差分 | 不需要双向协商 |

**可检查的判据**：存在一张 `beat` 记录表；"最后一次成功同步 / 连续失败次数 / 失败在哪一跳"三样能在同一处读出；网络不可达**不得**被写成"不算失败"。
