# 「空间与设置 → 定时与提醒」规划（2026-10-15）

> 用户要求：**把底层配置放到「空间与设置」里面，就是对应的一些闹钟、定时等，这个要做好规划。**
> 状态：**规划完成，待实现**

---

## 1 · 放在哪：不新增入口

「空间与设置」是个**弹窗**（`inbox.openSettings()`），里面**已经有**：

| 现有小节 | 内容 |
| --- | --- |
| 数据根目录 | 数据实际落在哪个文件夹（根目录配错时一眼看出） |
| 目录授权 | 哪些文件夹可读/可写 |
| **主动做事** | 心跳留痕、「该说没说」反馈、出声额度、免打扰时段 |
| 收件箱 | 待确认数量与入口 |

**「定时与提醒」与「主动做事」是同一类东西**（都是"它什么时候主动找你"），所以：

```
空间与设置
  ├─ 数据根目录
  ├─ 目录授权
  ├─ 主动做事        ← 已有
  └─ 定时与提醒      ← 新增，紧挨着「主动做事」
```

**理由**（宪章第六条·克制）：**新元素必须证明无法被现有元素表达**。
「定时」和「出声额度/免打扰」回答的是同一个问题——**它什么时候出声**。
另开一个入口就是把这个问题的答案劈成两半。

---

## 2 · 放什么：三件，不多

| # | 显示什么 | 数据来源 | 为什么是它 |
| --- | --- | --- | --- |
| A | **已安排的定时任务清单** | `schedule_list` | 用户要能看见"它到底替我排了什么"。**看不见的定时＝不知道它什么时候会响** |
| B | **新建一条**（时间 + 做什么） | `schedule_create` | 常见改动就地完成（用户硬要求）：加一条不用去别处 |
| C | **每条可停/可改/可删** | `schedule_update` / `schedule_delete` | 撤销与可退（03 §3） |

**明确不放的**：
- ❌ 出声额度 / 免打扰 —— **已经在「主动做事」里**，这里重复就是两处出现同一信息
- ❌ cron 表达式、时区、重试策略 —— 内部概念，不是用户要的东西（`03 §7 禁造词`）

---

## 3 · 每条怎么显示（沿用现有措辞口径）

```
每天 09:30   做一份简报            [停]  [改]  [删]
每天 21:00   做一份简报            [停]  [改]  [删]
周一 08:00   提醒我本周的三个节点   [停]  [改]  [删]

＋ 新建定时
```

**判据**（逐条可查）：
- **时间说人话**：「每天 09:30」「周一 08:00」，**不显示 cron**（`wording-audit` 的禁词表里加 `cron`/`crontab`）
- **没任务就不摆空位**：没有定时任务时用 `emptyState`（简笔画 + 一句状态 + 一个下一步），不显示空列表（宪章六·安静）
- **服务没接上要说实话**：拿不到 `schedule_list` 时写「读不到定时任务：<原因>」，**不给假按钮**（约束三·未接入不伪造）
- **每条有明确开关**：停用 ≠ 删除，两者都要有（克制：不要一删了之）

## 5 · 实现顺序（每步都能单独验收）

| 步 | 做什么 | 验收 |
| --- | --- | --- |
| ① | `browser-api.mjs` 透传 `schedule_list` / `schedule_create` / `schedule_update` / `schedule_delete` | 本地真调一次，拿到真实列表 |
| ② | 「空间与设置」加「定时与提醒」一节：**只读列表** | 真实浏览器打开设置，看到列表或"还没有定时任务" |
| ③ | 加「新建」+「停/改/删」 | 真建一条 → 列表出现 → 停用 → 状态变 → 删除 |
| ④ | 门禁：`spec-coverage-audit` 挂到 `03 §2 交互律 01`（常见改动就地完成）；`wording-audit` 加 `cron` 等禁词 | `npm run verify` EXIT=0 |

**①之前必须先做**：确认 `schedule` 服务暴露的**接口形状**。
### ⚠️ 本轮查证结果：我原规划的第一步写错了

查 mini 上的 `dsh-schedule` 包，它注册的是 **Agent 工具**：

```
schedule_create · schedule_list · schedule_delete · schedule_conflict · schedule_log …
```

**这些是给「智能体」用的工具，工作台插件调不到。**
我原规划写的「`browser-api.mjs` 透传 `schedule_list`」**是错的**。

**同时**：`/api/schedule` 与 `/api/schedule/tasks` 都返回 **401（路由存在）**，
说明**另有一套 HTTP 接口**（大概是给 `ui-schedule` 客户端页面用的），
**但它的请求/响应形状我没验**（要认证）。

### ✅ 本轮查清了正确接法（推翻"调 /api/schedule"）

读 `dsh-client-ui-schedule` 的客户端代码，它走的是 **`/call`** —— **DSH 的服务调用桥**，不是 REST。

**所以正确接法是：工作台插件「注入 `schedule` 服务」**，再经自己的 browser API 暴露给界面。
DSH 插件之间本来就是这么声明依赖的（我的插件已经在注入别的 DSH 服务）。

```
✘ 错的：工作台去 HTTP 调 /api/schedule
✔ 对的：工作台 inject 宿主服务 `schedule` → 经自己的 browser API 暴露
```

**实现要动两处**（都在我掌控内）：
1. 插件清单里把 `schedule` 列为**可选依赖**（没有调度 bundle 时插件照常启动，只是这一节显示"未接入"）
2. `browser-api.mjs` 加一组动作，转调 `schedule.list` / `create` / `update` / `delete`

**关键约束**：**可选**。没有它就装不了的插件，等于把工作台和实验性 bundle 绑死 ——
而那是个 experimental 包（`约束三·未接入不伪造`：没接入就如实说没接入，不给假按钮）。

### 所以第一步改成

**先弄清 `/api/schedule` 这套 HTTP 接口的形状**。在那之前：

- **界面一行都不写** —— 没验接口就写界面，写出来的是**一堆假按钮**（约束三·未接入不伪造）
