### A-1 修 `rootDirectory` 读不出来（真 bug，用户可见）

| 项 | 内容 |
|---|---|
| 现象 | 设置页「数据根目录」显示 **微信工作区**（配置里写的是 飞书工作区）；「读文件」显示可读写的文件夹是 `test` |
| 根因 | `rootDirectory` 在 Config schema 里标了 `.volatile()`，宿主物化后传进来的是 `{get(){…}}` **不是字符串**；`resolveConfig` 按 `typeof === 'string'` 读 → 拿到空串 → `rootWorkspaceId()` **静默回退**成"第一个已授权工作区"（9359d460 微信工作区） |
| 证据 | `new Config({rootDirectory:'/…/飞书工作区'}).rootDirectory` → `typeof = object`；旧写法判字符串 → false。见 `test/root-directory.test.mjs` |
| 为什么门禁没抓到 | 既有测试喂的是**普通字符串**（YAML 形态），与宿主真正给的东西不同形 |
| 修法 | `unwrap(config.rootDirectory)` 后再判字符串；新增 3 项回归测试（含"用真 schema 物化"这条路径） |
| 附带 | 根目录与注册表对不上时**不再静默**：`rootStatus()` 把「配置声明的根」「实际用的工作区」「是否回退」一起报出来，设置页用 warning 文字如实说明 |

## 同步语义实测：并发的"改"赢不过"删"；但**删除能被撤销却查不到**

继续查同步线，这轮把"多端同时改同一条"的真实语义量清楚了，并抓到一个**静默的治理缺口**。

### ① 一端删、另一端并发改过同一条 → **删除生效**（这是对的）

```
同步前：本地 实体无 / 墓碑 rev 3      对端 实体 rev 2（没看见删除，还在改）
引擎判定：取本地（本地已删除（墓碑较新）：2 → 3）
同步后：两端 实体都无 · 两端墓碑都是 rev 3 · **两端各一条 sync.override 留痕**
        （写明 winner=local · loserRevision=2 · winnerRevision=3 · 理由）
```

**为什么删除一定赢**：墓碑写入时带的是「实体版本 + 1」，所以它天然比"基于旧版本的一次改动"更新。
这正是宪章 F14「删除不复活」要的。

> 我第一版**把期望写反了**（以为"对端改过"就该保住实体），测试当场变红，才发现是自己理解错。
> 教训：**测出来的"不符合预期"先怀疑预期**。

### ② 但对端改得足够多（版本号超过墓碑）时，**删除会被撤销** —— 而且原来**两端一条留痕都没有**

```
同步前：本地 墓碑 rev 3          对端 实体 rev 4（连改 3 次）
引擎判定：删除后被改过（按新证据保留）↺ project p-1
同步后：两端实体都回来（rev 4）· 墓碑撤掉 · 原来 audit 里 **0 条**记录
```

用户会看到**自己删掉的东西回来了，却查不到为什么**。删除被撤销比改动被覆盖更该留痕。

**修法**：新增事件 `sync.resurrect`，两端各写一条，含
`{id, kind, decision:'kept-after-delete', tombstoneRevision, winnerRevision, reason}`；
计划里补上 `tombstoneRevision` 字段（原来只有 revision，留痕写不出"当时墓碑是几版"）。

**验收**（新增测试，两端都断言）：留痕存在 · `decision` 正确 · 墓碑版本是数字 · 理由非空。

> 这一条也顺手回答了一个你可能想知道的设计问题：**"删除"不是绝对的** ——
> 对端在删除之后若又改了几轮，那些改动会被当成"新证据"，把删除撤销掉。

> 如果你更希望"删了就是删了"，这是**一条可以改的设计决定**，说一声我就改。

## 同步前的"快照"根本不是备份（**会静默丢掉最近一步**）　✅ 已修

这轮查同步/多端这条线（唯一还没在真机两端跑过全链的部分），第一站就撞到真问题。

### 现场

`sync-engine.mjs` 在真同步前会打快照，界面上写的是「**安全前提②：写前给两端各打一份快照。出事能回退。**」
实现是：

```js
copyFileSync(LOCAL, localSnap);     // ← 只拷主文件
```

**而库跑在 WAL 模式，且插件进程一直开着它。** 最近提交（有时连建表）还在 `-wal` 里没落盘 ——
只拷主文件得到的不是"旧一点的备份"，而是**缺东西的备份**。

### 两次实测（都不是推测）

| 情形 | 旧做法拷出来的"备份" |
|---|---|
| 新建库、进程开着 | **连 `entities` 表都没有** —— 打都打不开 |
| 真实库副本（schema 早已落盘）、同步前刚提交一步 | 真库 **32** 个对象 · 备份里 **31** 个 —— **少的正是"同步前刚做的那一步"** |

磁盘上现存 7 份 `.syncbak-*`：都能打开，但**全是旧的**（19 个对象，而真库现在 31 个）。

### 修法

改用 **`sqlite3 .backup`**（在线备份，天生处理 WAL），并在打完之后**校验一遍**（能打开、表在）；
拿不到 sqlite3 就**如实报错并中止同步**，绝不退回"拷主文件"这种看起来成功、实际没用的做法。
对端同理（远端也走 `sqlite3 .backup`）。

### 验收

新增测试：**保持写入连接开着**跑一次同步，然后打开那份快照，断言它有 `entities` 表、且对象数不少于最新提交。

```
修复后：PASS
旧做法：FAIL（快照打不开 / 少对象）—— 对照实验，证明这条测试咬得住
```

> **写这条测试时我自己又踩了同一个坑**：造"对端库"用了 `/bin/cp`，而当时 store 还开着 →
> 对端库没有表，引擎当场报 `no such table: entities`。测试里的建库也改成了 `.backup`。

**教训（第三次了）**：WAL 模式下**任何**复制数据库的动作（备份、取副本、造对端）都必须走 `sqlite3 .backup`，
`cp` 只能用于**已经关库**的情形。

## 22px 间距：同类问题，但这次**确实渲染**了 —— 已收敛

审计说「VI 间距标尺（4/8/12/16/24/32/48/64/96）里没有 22，但原型在用」，登记表把它放在 `contractValues` 里合法化。

### 关键发现：间距门禁**根本不查 margin**

`measure-page.mjs` 原来只查 `padding` 与 `gap` —— 而 22px 恰恰写在 **`margin`** 上
（`.sectionhead` / `.footer` / `.drawer h2` / 任务区，共 4 处，**包括一处内联 `style="margin-bottom:22px"`**）。
所以"间距标尺"这道门禁**永远看不见它**，它才能在登记表里安然合法化。

### 修法

| 步 | 做了什么 |
|---|---|
| 1 | **门禁补上 margin**：并明确三类不算我们写的 —— `auto`（按**声明值**排除，因为计算出来的像素是 44/204/278 这种，看不出是 auto）、**浏览器给表单控件的默认边距**（**逐边**比对 UA 默认：checkbox 是 `3px 3px 3px 4px`，我们只改了 top，整串比对会漏）、**已登记的信息架构度量**（侧栏宽 204 等，由 craft-audit 从 registry 传入） |
| 2 | **收敛 22px → 24px**（生成期，含内联属性；差的 2px 是纵向节奏） |
| 3 | **撤掉 `contractValues` 里 22px 那条**：它不是"被测试断言的契约值"，只是原型节奏 —— 放在那里是**归类错误** |

**这次会动到视觉**（不像圆角几乎全是死声明），所以逐项验过：`geom-diff`（锚点 ≤2px）✅ · `craft-audit` ✅ ·
`pixel-diff` 棘轮（未比基线更差）✅ · `mobile-audit` ✅ · 655 项测试 ✅。

> 过程里踩的坑：第一版只替换了 `margin:22px` 与 `margin-bottom:22px`，
> **漏了 `padding-inline:22px` 和内联 `style="..."`** —— 门禁当场报出残留，才补全。

## 审计第 11 条 · VI §9 **画布缩放分层**（真 bug，不是旧构建的锅）　✅

## 严重事故与修复：真定时让插件**启用失败**（2026-10-16 晚，用户重启时）

**现场**：用户重启后弹「启用失败：`ReferenceError: heartbeatMinutes is not defined`」——
**我装上去的代码把整插件打挂了**。

### 根因（两个错，第二个更值得记）

1. **跨作用域引用**：`heartbeatMinutes` 声明在 `resolveConfig` 里，却在另一个函数 `apply` 里直接用。
   两个函数各是各的作用域 → 真实宿主上一启动就抛错。
2. **门禁为什么没拦住 —— 它比真实宿主弱**：`activation-replay` 的假 ctx 里 `get()` **一律返回 `undefined`**，
   而宿主**真的有 `timer` 服务** → `Boolean(timer) && heartbeatMinutes>0` **短路**，那行根本没被求值 → 重放报 PASS。
   **"重放通过"只证明了"在假 ctx 里通过"**，而假 ctx 缺了宿主的一个真实服务。

### 修法

| 层面 | 做了什么 |
|---|---|
| 代码 | `resolveConfig` 把 `heartbeatMinutes` 随返回值带出；`apply` 里 `const heartbeatMinutes=resolved.heartbeatMinutes`（同作用域，先声明后使用） |
| **门禁** | `activation-replay` 的宿主桩**补上 `timer`**（对齐宿主真实能力）—— 补上之后立刻抓出两个真实错误 |
| 防复发 | 新增 2 项测试：① 重放桩必须提供 `timer`；② 定时变量必须先声明后使用（`test/heartbeat-schedule.test.mjs` 共 6 项） |
| 旁证 | 静态扫了一遍 `resolveConfig` → `apply` 的跨作用域引用，确认没有同类残留（3 处报的是注释与属性名，非真引用） |

### 教训（写进 MEMORY）

**宿主桩的能力必须对齐真实宿主**。桩比宿主弱时，凡是"只在有某服务时才走到"的代码都会被整段跳过，
于是门禁报绿、用户一启动就炸。**凡新增"依赖宿主某服务"的分支，都要同步给桩补上那个服务。**

**现场**（在真实库里看到的）：你的收件箱里躺着 **3 条一模一样的「谁能看 · 服务器方案当前并不存在…」**，
都写着 `expectedRevision 1`，而那条判断**已经是 revision 5、share 也早就是 team** ——
也就是说：**这三条改动早就直接生效了，收件箱里躺着的是一堆"已经做完的事"**，而它们点「同意」必然冲突。

**根因**（`prototype/batch.mjs` 的 `apply`）：走 draft → commit；一旦 commit 报版本冲突，
它会**另建一份草稿**用最新版本重放并提交 —— 但**原来那份冲突草稿留在原处**。
于是**每冲突一次，收件箱就多一条僵尸**。

这与用户 2026-10-12 拍板的契约正面冲突：
「**自己的操作直接生效（不进收件箱），只有 AI 提议才进收件箱**」。

**修法**：冲突重放**成功之后**，撤掉那份冲突草稿（撤不掉只 `catch` 掉，不影响"已保存"的语义；
断网/超时的失败路径照旧保留草稿与重试，不误伤）。

**回归测试** `test/apply-no-zombie-draft.test.mjs`（3 项，含"必须先确认重放成功再撤"的顺序要求）。

## 批次 D · 假死判据　✅ 完成（真定时仍受阻，如实标注）

### D-1 为什么"假死"必须单独立一条

### D-2 修法：加"沉默多久"，并且只在"承诺过"时才算数

| 情况 | 判定 |
|---|---|
| **没接定时** | **不报假死** —— "多久没醒"从来没有承诺过，报它是冤枉（诚实要求）。但沉默时长照样算出来，界面看得见 |

| 接了定时、一次都没成功过 | **报假死**（不是"没记录所以没事"） |
| 接了定时、刚跑成功过 | 不报 |
| 连续失败 | 照旧告警，带失败原因 |

- 新增 5 项测试（`test/heartbeat-stall.test.mjs`）

- **把判定逻辑抽成纯函数** `sync-plan.mjs`：原来它跟 ssh/SQLite 绑死、**没法测**，所以这两个数据丢失级 bug 一直没被发现。抽出来后 7 项单测覆盖全部分支。
- **让引擎能被端到端测**：加了 `--remote-local <db>`（把对端当本地文件，只用于测试）。

### 端到端实测（两台真实 SQLite）

```
① 只读检查 → 「对端新增 0」·「对端删除 p-2」      ← 修复前这里会把 p-2 当"对端新增"拉回来
② --apply  → B 库的 p-2 被删 · 墓碑两边都在 · **两端各有 1 条覆盖留痕**
③ 再跑一次 → 纯无操作（0 新增 / 0 冲突）           ← 幂等，可安全反复跑
```

### 一条诚实的保护（重要）

真实库**现在还没有 tombstones 表** —— 因为运行中的实例还是旧代码（不写墓碑）。所以引擎现在会：

- 两端的墓碑表**缺任何一侧** → **拒绝 `--apply`**（exit 4），并说明"两端各重启一次再跑"；
- 只读检查照常，但明确标注"删除判定不可信，仅作参考"。

理由：分不清"这边删了"和"那边新增的"时，拉过来会复活删除、推过去会误删对端，**两种都会丢数据。宁可不做。**
